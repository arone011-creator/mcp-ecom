The storefront's half of "one agent, with a chat UI". Written 29 Aug 2026.
================================================================================

M4 is split across two repositories, because the work genuinely is.

    THIS PLAN          the storefront: token refresh, the chat UI, the event
                       stream to the browser, and the approval control
    THE OTHER PLAN     mcp-ecom-agent-layer/docs/PLAN_M4_AGENT.txt - the
                       agent itself, its evaluation harness, and its deploy

Neither is complete alone. Read both before starting either.

    IN PLAIN TERMS
    The next stage adds an AI assistant customers can talk to. Half that
    work is the chat window and the "are you sure?" button, which live in
    the shop. The other half is the AI itself, which lives in the other
    project. This document covers the shop's half.


WHAT THIS PLAN IS, AND IS NOT
-----------------------------
It is a TASK-LEVEL plan: what to build, in what order, which files, what
each task must prove before it is done, and which decisions must be made
first.

It is NOT a step-by-step script with the code pre-written. That is
deliberate, and it is this project's own hard lesson: the M3 plan was
written against the real code rather than against design documents, and
that is what caught three places where the design was wrong about its own
system. Writing the UI code now, against components that do not exist and a
streaming contract not yet frozen, would produce confident fiction.

Write each task's step-level plan against the real code, at the time.

    IN PLAIN TERMS
    This lists what to build and in what order, not the finished code.
    Writing the code in advance - before the parts it depends on exist -
    has already been proven on this project to produce plans that are
    wrong in ways nobody notices until late.

================================================================================
1. DECISIONS THAT MUST BE MADE FIRST
================================================================================

Four. Each changes the task breakdown, so settle them before Task 1.

(A) WHERE DOES THE AGENT LOOP RUN?

    The chat UI is Next.js. The agent is Python. Something must sit between
    them. Two options:

      1. The browser talks to a Next.js route, which talks to the agent
         service over HTTP. One public surface, session cookie already
         present, CORS is not a problem.

      2. The browser talks to the agent service directly. Fewer hops, but
         a second public service handling browser sessions, and the
         approval control would live outside the app that authenticates
         the user.

    RECOMMENDED: option 1. It keeps every browser-facing concern in the
    storefront, which is the thing that already knows who is signed in.
    It also keeps the approval mint reachable only from server-side code.

(B) WHO MINTS THE APPROVAL - AND IT MUST NOT BE THE AGENT.

    This is the load-bearing decision of the whole milestone.

    The MCP server refuses a high-risk call without an approval token, and
    mints tokens from an HTTP route that is deliberately not an AI tool. But
    "not a tool" only helps if the agent process cannot make arbitrary HTTP
    calls to that route.

    THE RULE: the approval is minted by the Next.js route handler, after a
    human clicks, and handed to the agent as the argument of the next tool
    call. The agent never holds the ability to mint one.

    If the agent process can reach /approvals, the entire mechanism is
    theatre. Write a test that asserts the agent's egress cannot.

(C) HOW DOES THE BROWSER GET A BEARER TOKEN?

    The MCP server needs one, and it cannot be the seven-day default -
    these tokens cannot be revoked. Phase 2 owes a refresh mechanism
    (decided during M3, recorded in docs/mcp/phase-2-single-agent.md).

    RECOMMENDED: the browser never sees a bearer token at all. The Next.js
    route holds the session cookie, mints a fifteen-minute token
    server-side per request, and passes it onward. Nothing long-lived
    exists in the browser, and "refresh" becomes "mint another one",
    which needs no new storage.

(D) WHERE DOES THE CONVERSATION LIVE, AND HOW DOES IT SURVIVE NAVIGATION?

    The assistant is available from every page, not one dedicated route -
    a floating entry point, not a destination. That means the conversation
    and its streaming connection cannot be owned by a page component; a
    route change would tear both down.

    RECOMMENDED: a single provider mounted once in app/layout.tsx, holding
    the message history and the open connection to /api/assistant. Every
    page renders the same floating widget reading from that provider.
    Closing the widget hides it; it does not unmount the conversation.

    IN PLAIN TERMS
    Four things to decide before building. The most important: the AI
    must not be able to approve its own actions. A human clicks the
    button, and the shop - not the AI - issues the permission slip. If the
    AI could issue its own, the whole safety design would be decoration.
    The fourth: the chat needs to live "above" any one page, the way the
    header does, so clicking around the site does not reset it.

================================================================================
3. THE EVENT CONTRACT - FREEZE IT BEFORE ANYTHING CONSUMES IT
================================================================================

The design document is explicit that this is the cheapest thing to get
wrong: the chat UI, the agent, and Phase 3's pause-and-resume payload all
depend on the same event shape.

    tool_started        which tool, and the arguments, STRUCTURED
    tool_completed      which tool, and a summary of the result
    approval_required   which tool, the arguments, and a token handle
    message             assistant text
    error               something failed, and whether a retry is sensible

FOUR RULES THAT ARE NOT NEGOTIABLE:

  1. THE APPROVAL CARD IS RENDERED FROM THE STRUCTURED ARGUMENTS, NEVER
     FROM AGENT PROSE. Product descriptions and reviews are written by
     strangers and reach the agent's context. If the agent writes the words
     next to the button, an injected review can write them too. The card
     shows the order number the API returned - not a sentence the model
     composed.

  2. VERSION THE SCHEMA FROM THE FIRST COMMIT. Phase 3 consumes it too.

  3. CHAT-DRIVEN CHANGES UPDATE THE SAME DATA THE REST OF THE SITE READS,
     NOT A PRIVATE COPY. A tool_completed event for a cart or order change
     invalidates the same cache/query the manually-clicked cart page and
     header badge already use. Two copies of "what's in your cart" is a
     worse bug than a stale one - it lies to the customer about which
     answer is real.

  4. THE ASSISTANT NEVER NAVIGATES, FILTERS, OR SIGNS THE CUSTOMER IN OR
     OUT ON ITS OWN. It can show a link to a product; it does not route
     the customer there itself. A page changing underneath a customer
     without them acting is worse than the assistant not doing it at all.

    IN PLAIN TERMS
    The chat window shows what the AI is doing as it happens. The rule
    that matters most: the confirmation box must be built from real data -
    the actual order number - and never from a sentence the AI wrote. A
    review written by a stranger could otherwise put misleading words next
    to the confirm button. The other two rules keep the assistant from
    ever lying about what is really in your cart, or taking you somewhere
    you did not ask to go.

        mcp-ecom-agent-layer/contracts/assistant-events.v1.json

    "The two must agree exactly" is enforced by an artefact rather than by
    two prose descriptions, because separate repositories in different
    languages have no module to share. That JSON file holds a recorded
    stream covering all five types beside the conversation replaying it
    must produce. The agent repository already executes it in Python.

    THIS TASK: vendor that file into the storefront and assert the
    TypeScript reducer reaches the identical `expected` conversation.
    A shape change on either side then reddens tests on that side, which
    is the point - keep the copy byte-identical rather than tidying it.

    TWO THINGS THE AGENT WILL NEVER SEND, contrary to section 3 above:

      * approval_required carries NO token handle, only call_id. Section
        3's summary line says "a token handle", but Task 5 below has the
        approve route mint AFTER a human click, from the arguments in the
        event. A handle minted by the agent would be the agent taking
        part in its own approval. call_id is enough: the event names
        WHICH order, and Task 5's fresh server-side lookup answers WHAT
        is true about it.

      * tool_completed carries NO cache-invalidation hint. Rule 3 still
        holds, but the tool -> cache-key mapping is written HERE. The
        event carries `tool` and `ok`; this side maps. An agent shipping
        cache keys would be asserting facts about a UI it cannot see.

    Also settled there and worth knowing before building the widget:
    every tool_started is guaranteed a tool_completed, including a call
    the agent refused to run, so a chip never spins forever; and a
    missing `seq` is reported as a gap rather than smoothed over,
    because a dropped event means the screen is not showing what
    happened.

    BUILT. lib/assistant/events.ts, with the golden stream vendored
    byte-for-byte at lib/assistant/assistant-events.v1.json. The
    TypeScript reducer reaches the identical `expected` conversation the
    Python one does; that assertion is the cross-repository anchor, and
    it was mutation-checked rather than assumed -- removing the
    duplicate-call guard makes it fail.

    THE DIVISION OF LABOUR, which Task 4 needs to know:

        parseEvent(raw)   -> AssistantEvent | null.  NEVER THROWS.
        replay(events)    -> Conversation.  Sees only parsed events.

    A null from parseEvent means DROP THIS FRAME AND KEEP GOING. It is
    not an error to surface and not a reason to stop reading the stream.

    ONE DELIBERATE ASYMMETRY WITH THE PYTHON, recorded so it does not
    read as drift later. agent/events.py::replay THROWS on an event from
    a future schema version -- right for a harness, which should stop
    loudly when handed something it does not understand. Wrong here: a
    throw mid-stream leaves the customer with half a conversation and no
    way forward. So this half drops the frame instead, and the module
    header says why.

    Fourteen malformed inputs are covered, including a future version, a
    fractional seq, an array, and a missing data object. 258 unit tests
    pass; type-check clean.

TASK 2 - SHORT-LIVED TOKENS FROM A SESSION, WITHOUT A PASSWORD    [DONE 2026-09-03]
    POST /api/v1/auth/refresh: read the session cookie, mint a 15-minute
    bearer. Reuse the ttlSeconds clamp added in M3.
    MUST PROVE: 401 without a session; the minted token is accepted by
    /api/v1/auth/whoami; the lifetime is 15 minutes, not 7 days; and the
    route never accepts a password.

    ALL FOUR PROVED. AND A FIFTH, WHICH THIS PLAN DID NOT ASK FOR AND
    WHICH DECIDES WHETHER THE OTHER FOUR MATTER:

        THE ROUTE MUST REFUSE A BEARER TOKEN.

    The obvious implementation calls requireApiUser, because every other
    v1 route does and its own header calls it "the single identity choke
    point". But requireApiUser accepts a bearer OR a cookie -- and a
    bearer is exactly what this route issues. Wired that way, the agent's
    own 15-minute token can call /refresh and receive another 15 minutes,
    indefinitely. The token stops expiring, and every reason the lifetime
    is short evaporates: these JWTs cannot be revoked, and rotating
    NEXTAUTH_SECRET is the only kill switch and signs out every browser.

    So this route calls getToken directly. Cookie only. A browser may
    refresh; a token may not. That reasoning is in the route's own header
    as well as here, because a future reader tidying it to match the
    other routes would silently create an un-expiring token.

    Mutation-checked rather than assumed: swapping getToken for
    requireApiUser makes the test fail, which is the point of having it.

    TWO SMALLER DECISIONS
      * The route NEVER READS A REQUEST BODY. Not "rejects a password" --
        never parses one, so there is nothing to bypass and nothing to
        regress. A body carrying email and password changes nothing.
      * The lifetime is not caller-controllable. clampTtl exists so a
        caller can ask for LESS than a long default; here there is no
        default worth shortening. A test asserts REFRESH_TTL_SECONDS sits
        inside the token route's own bounds, so the two cannot drift into
        disagreeing about a sane lifetime.

    The response omits `user`. The browser calling this already knows who
    it is, and a route that hands back identity invites a client to trust
    it instead of /whoami.

    A per-user rate limit bounds a runaway client: 20 mints per 5
    minutes, which a widget refreshing a 15-minute token never
    approaches. In-process, so per replica -- the same limitation the
    token route's limiter already documents.

TASK 5 - THE APPROVAL CONTROL
    The approval card, plus POST /api/assistant/approve.
    MUST PROVE, and these are the tests that matter most:
      * the card's text is built from structured arguments, and an agent
        message containing markup or instructions cannot alter it;
      * the card's facts (order number, items, total) come from a fresh
        server-side lookup of the order by id, not from whatever the
        approval_required event's payload claims - the event names WHICH
        order, the lookup answers WHAT is true about it, so a compromised
        or manipulated event payload cannot misrepresent what is being
        confirmed;
      * the approve route mints for the EXACT arguments in the event, not
        arguments supplied by the caller;
      * a second click does not mint a second approval;
      * declining sends nothing to the MCP server;
      * nothing anywhere shows the action as completed until the server
        confirms it happened - a High-risk action never renders
        optimistically, unlike a Low/Medium tool result, which may.

TASK 6 - RICH RESULTS AND PROGRESS
    Product cards and order cards instead of prose, per the design's UX
    list. Render from tool results, not from agent text - same reason as
    the approval card.

    Also from that list, and easy to forget because they are not features
    so much as manners:
      * SHOW THE PLAN for a multi-step request, updating as steps complete.
        Visibility into what it intends, without exposing raw reasoning.
      * PROGRESS INDICATORS for longer flows, INCLUDING FAILURE STATES with
        explicit recovery options - Retry, Choose another, Cancel. A flow
        that can only succeed visibly and fails silently is worse than one
        that never started.
    MUST PROVE: a failed tool call produces a visible failure with a way

    through the assistant is visible on the actual cart/orders page

    a manual action would (Rule 3, section 3) - never a private copy the
    chat keeps to itself.

    MUST PROVE: the options come from a tool result, so the customer can

    Do not design it again. metrics/agent-evals.json:

          "generatedAt": "2026-09-03T09:14:02Z",
          "model": "gpt-4.1",
          "runs": 5,
          "workflows": {
            "orders-recent": {
              "passRate": 1.0,
              "toolAccuracy": 1.0,

    loadAgent() is a copy of loadMcp(): read from disk, return null when
    the file is absent, so this harness still never needs a Python
    environment. It reads `.workflows`; the envelope exists because a
    pass rate means nothing without knowing which model produced it and

    IN PLAIN TERMS
    Eight steps, each finishing with a review. The order is deliberate:
    agree the message format, then the security plumbing, then a chat
    window that can only read things, and only then the button that can
    change something. The riskiest piece is built last, on top of parts

5. EXIT CRITERIA
================================================================================

    * A signed-in customer can hold a conversation that uses the low-risk
      tools and get correct, own-account-only results.
    * A cancellation requires a visible confirmation, and the confirmation
      text is provably not written by the model.
    * The agent cannot mint its own approval - asserted by a test, not by
      an assumption.
    * No bearer token is ever exposed to the browser.
    * The assistant is reachable from every page as a persistent widget,
      not a single dedicated route, and a conversation survives
      client-side navigation.
    * A cart or order change made through the assistant is visible
      everywhere else on the site immediately, through the same data path
      a manual action would use - never a private copy.
    * `npm run scorecard -- m4-single-agent --gate` exits 0.
    * The four workflows in docs/mcp/phase-2-single-agent.md pass in the
      eval harness (owned by the agent repo's plan).

    IN PLAIN TERMS
    Done means: a customer can chat with it, it only ever sees their own
    data, cancelling something needs a real click, the AI cannot give
    itself permission, and the health check still passes.

================================================================================

================================================================================
CHAT PERSISTENCE, PHASE 1 - CHRONOLOGICAL TRANSCRIPT    [DONE 2026-09-03]
================================================================================
    Not a numbered task in this plan. It came out of the persistence
    brainstorm (docs/superpowers/plans/2026-09-03-chat-persistence-roadmap.md)
    when the GPT-style layout requirement exposed a bug that was already
    shipped.

    THE BUG. The panel rendered every utterance, then every tool chip, then
    every assistant message - grouped by kind rather than by when. One
    exchange looks perfect, which is why no screenshot caught it. Two came
    out as Q1 Q2 A1 A2.

    The cause was in the contract, not the component: replay() returned
    three parallel lists (text, tools, errors) and so discarded the order
    events arrived in.

    WHAT CHANGED
      * replay() gained an ordered `timeline`, added the same additive way
        message_delta was: mirrored in agent/events.py and
        lib/assistant/events.ts, golden fixture re-vendored byte for byte.
        A tool is NAMED on the timeline, not embedded, because its state
        changes after it first appears and a snapshot would read "working"
        forever. One call is one item however many events it emits. A
        finished message replaces its fragments IN PLACE, so an answer
        keeps its position relative to tool calls that followed it.
      * The provider now groups events BY TURN rather than holding one flat
        array. Nothing else could say which reply answered which question.
        replay() runs once per turn and remains the only reducer.
      * The panel renders one block per turn: customer right, assistant
        left, in order.

    Mutation-tested on both sides: 4 mutations each, all caught, and the
    shared golden fixture catches most of them independently of the local
    tests - which is the entire reason that fixture exists.

    THIS GROUPING IS THE SHAPE PHASE 2 PERSISTS as ConversationTurn
    (utterance + events). It is not scaffolding.

    Phases 2-6 (storage and resume, history UI, titles, memory with a hard
    budget, summarisation) each get their own plan. The roadmap records the
    decisions so none of them is argued twice.

  2026-09-04 -- CHAT PHASE 2: STORAGE AND RESUME (plan
  docs/superpowers/plans/2026-09-03-chat-phase2-storage-and-resume.md)

    A conversation now survives closing the panel, a refresh, signing out
    and restarting the browser. Reopening the assistant shows the chat you
    were last having.

    WHAT CHANGED
      * Two tables, ONE migration: conversations and conversation_turns.
        The turn is the unit -- utterance plus the events that answered it
        -- because that is already the shape the provider holds, so
        persistence is append-only and hydration is one query.
        The migration also creates title, summary, summarisedThrough and
        agentContext, which nothing reads yet. Deliberate: schema changes
        against a live database are the riskiest step in this roadmap, the
        data model was settled in full during brainstorming, and four
        nullable columns now cost less than three more migrations later.
      * lib/assistant/conversation-store.ts is the ONLY place that touches
        these tables, and every query in it filters by userId inside the
        query rather than checking after it. That is structural, not
        stylistic: it is the M1 cached-order-read mistake.
      * The bridge accumulates the events it forwards and writes one row
        when the stream ends, awaited while the response is still open.
        Stored and forwarded are asserted to be the same events -- a record
        that disagrees with what was on screen is a second story about what
        happened. Control frames are withheld from the record exactly as
        they are from the browser.
      * The conversation is resolved BEFORE the bearer is minted or the
        agent is called, so someone else's conversation id costs a 404 and
        not a model call. It is created lazily on the first message, so
        opening the panel and changing your mind leaves nothing behind.
      * GET /api/assistant/conversations/latest takes no parameters at all.
        null is a normal answer, not a 404: everybody has a first visit.
      * The provider hydrates on mount and carries the conversation id,
        adopting it from the x-conversation-id response header. Stored
        events go through parseEvent -- the same door as live ones.

    Mutation-tested: 12 mutations across the store, the bridge and the
    provider, all caught.

    HOW THE MIGRATION REACHED PRODUCTION -- read this before the next one.
    prisma migrate deploy had NEVER run automatically on this project. The
    web service had no pre-deploy and no custom start command; the
    db:migrate:deploy script existed and a test asserted it existed, but
    nothing invoked it, so the schema was presumably applied by hand at
    some point. Option A was chosen: the web service now has a Railway
    pre-deploy command, `npm run db:migrate:deploy`. Every future deploy
    applies pending migrations before the new container takes traffic, and
    a failed migration blocks the deploy -- which is the correct failure.
    Deploy a2704c84 (commit fadd93a, 2026-09-04 06:26 UTC) reported
    "5 migrations found", applied 20260903190000_add_assistant_conversations
    and nothing else, and reached SUCCESS. So _prisma_migrations WAS
